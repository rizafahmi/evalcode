# Compile-gate viability finding

Spike for Task 2 of the evalcode build plan. Question: does a stock Phoenix
1.8 LiveView app compile clean under Elixir 1.20 with
`--warnings-as-errors`, so that Task 02's grading gate (`mix compile
--force --warnings-as-errors` exiting 0) can be applied to the whole
project rather than narrowed to specific paths?

## What was tested and what wasn't

Two things were compiled under the gate, in this order:

1. A stock `mix phx.new` app with no LiveView route at all — only Phoenix
   1.8's default HEEx scaffolding (`core_components.ex`'s
   attr/slot-annotated function components, `layouts.ex`,
   `embed_templates`-based `.heex` compilation).
2. The same app extended with a real, routed LiveView generated by
   `mix phx.gen.live` — the Task-9 shape: `mount/3`, `handle_event/3`,
   `stream`/`stream_delete`, and `~H` — compiled twice: once with its
   routes deliberately left unwired (reproducing an easy-to-omit manual
   step), and once with them wired into `router.ex`.

Both are reported below. The "global gate viable" decision is backed by
run 2's wired case, which is the shape Task 9's actual benchmark app and
Task 7's grader will exercise — not by run 1 alone. Run 1 is included
because it's still evidence (HEEx-generated code compiled clean there
too), but on its own it doesn't cover LiveView specifically and should not
be read as sufficient by itself.

Not tested: `order_live/`-specific business logic (that's Task 3's actual
LiveView, not a generic scaffold), and any other Elixir-1.20-inference
false positive that might arise from patterns `phx.gen.live` doesn't
generate. If Task 3's real LiveView modules trigger a warning neither of
these runs did, that would be new information contradicting this finding.

## Run 1: stock app, no LiveView route

```bash
cd gatecheck
mix compile --force --warnings-as-errors
```

**Exit code: 0.**

Full captured output (`--force` recompiled all of the app's 14 `.ex`
files, including the HEEx-embedding modules `core_components.ex`,
`layouts.ex`, and `page_html.ex`, which pull in `layouts/root.html.heex`
and `page_html/home.html.heex` via `embed_templates`):

```
Compiling 14 files (.ex)
Generated gatecheck app
exit=0
```

No warnings anywhere in the app's own modules.

Repeated from a fully deleted `_build/` (forcing Phoenix, LiveView, Ecto,
Gettext, Bandit, etc. to recompile from source alongside the app) to rule
out a stale-build false positive: exit 0 again. That run did emit
warnings, but only from third-party dependency compilation
(`telemetry_metrics`, `phoenix_template`, `dns_cluster`, `gettext`,
`phoenix_live_dashboard`) — never from `lib/gatecheck/` or
`lib/gatecheck_web/`. `mix`'s `--warnings-as-errors` flag governs only the
compilation of the current project, not `mix deps.compile`; dependency
warnings print but don't affect the gate's exit code. This confirms the
clean result isn't cache-dependent — the app's own code was warning-free
in both a warm-cache and a from-scratch run.

## Named constraint for later tasks: `~p` route resolution is a distinct failure mode from type inference

Section 2a demonstrates a real, separate way `mix compile --force
--warnings-as-errors` can fail that has nothing to do with Elixir 1.20's
type-inference false positives this spike was chartered to investigate:
**every `~p` verified-route call in the graded codebase must resolve
against a route actually declared in `router.ex`, or the compile fails.**

This matters for later tasks because:

- **The gate cannot tell the two failure modes apart from the exit code
  alone.** `mix compile --force --warnings-as-errors` exiting 1 means
  "there are warnings," full stop — it says nothing about whether those
  warnings are type-inference false positives (the risk this spike
  investigated) or unresolved `~p` targets (an entirely different,
  much more mundane mechanism: a missing router entry). A grader reading
  only the exit code, or even scraping for the word "warning," cannot
  distinguish "the model fixed the type violations but left a route
  unwired" from "the model failed to fix the type violations." Anyone
  building `bin/evalcode grade` (Task 7) or authoring Task 9's benchmark
  and its reference solution needs to either guarantee routes are always
  fully wired in both the seeded task state and any acceptable solution,
  or parse warning text well enough to attribute each one to its actual
  cause rather than trusting the exit code as a single undifferentiated
  signal.
- **This is a constraint on how the codebase-under-grade must be
  constructed, not a reason to narrow the gate.** Unlike a genuine
  type-inference false positive in generated/macro code (which a
  developer cannot fix and which would force narrowing the gate's scope),
  a `~p` route mismatch is fully within the author's/model's control to
  avoid — every `~p` target used anywhere in the graded app must have a
  matching route. Task 9's seed state and reference solution must satisfy
  this, and if the benchmark task ever asks a model to add or move a
  LiveView page, the task must make clear that routes need to stay wired,
  since an unwired route will fail the gate for a reason unrelated to
  what Task 02 is meant to measure.

## Decision

> **Decision: global gate viable.** A stock Phoenix 1.8 LiveView app
> compiles clean under Elixir 1.20.2 with `--warnings-as-errors`. Task 02
> grades on whole-project compile.

This is backed specifically by run 2b: `mix compile --force
--warnings-as-errors`, the exact gate command, exited 0 with zero warnings
against a real, routed LiveView of the Task-9 shape (`mount/3`,
`handle_event/3`, `stream`/`stream_delete`, `~H`) generated by `mix
phx.gen.live` with no code changes beyond wiring the four routes the
generator itself instructs you to add — reproduced from both a warm build
and a fully deleted `_build/`. Run 1 (stock app, HEEx scaffolding only, no
LiveView route) is corroborating but was not, by itself, sufficient
evidence for a LiveView-specific gate — run 2b is what closes that gap.

The decision is conditioned on the named constraint above: it holds only
for codebases where every `~p` target resolves. Task 9 and Task 7 must
account for that separately from whatever Elixir 1.20 type-violations the
benchmark task itself is about.
