# evalcode — Design

**Date:** 2026-08-02
**Status:** Approved, pending implementation plan

## Problem

When a new LLM is released, there is no repeatable way to answer "how good is this at *my* kind of work?" Public benchmarks measure Python and JavaScript on code the model has likely memorised. This project builds a private, reusable benchmark: a purpose-made Elixir/Phoenix codebase, a fixed set of coding tasks graded by tests, and a harness that records results so models can be compared over time.

## Approach

A human-driven benchmark. The harness prepares an isolated workspace and hands over a task; the operator opens their own coding agent — with whatever model is under test — and works the task. The harness then grades by running tests the agent never saw, and appends a result record.

The harness does not call model APIs. It builds workspaces, grades them, and reports.

## Scope

**In scope for v1:**

- A fixture Phoenix application (`Warung`)
- 12 tasks in two tracks: 7 domain, 5 type-system
- An `evalcode` CLI: `list`, `start`, `grade`, `report`, `verify`
- Results in append-only JSONL, plus a generated `LEADERBOARD.md`
- Nix flake and direnv setup pinning the toolchain

**Explicitly out of scope for v1:**

- Token capture. The results schema reserves a `tokens` field, always `null` in v1. A collector can be added later without a schema migration.
- Automated agent invocation. The operator drives their own agent.
- HTML dashboards. The JSONL schema is stable, so one can be generated later from the same data.

## Toolchain

| Component | Version | Notes |
|---|---|---|
| Elixir | 1.20.2 | Pinned via flake. Gradual set-theoretic types are central to Track B. |
| Erlang/OTP | 27 | Matches the `elixir_1_20` build in nixpkgs. |
| Phoenix | 1.8 | `mix phx.new warung --no-html --no-assets --no-mailer --database sqlite3` |
| Database | SQLite via `ecto_sqlite3` | Database is a file inside the run directory. |
| Harness | Elixir escript | Same toolchain as the fixture; no second runtime. |

Elixir 1.20 performs type inference and gradual type checking with **no user-facing annotation syntax** — explicit type signatures do not exist in this version. Type tasks are therefore about making code survive the inference engine, never about writing signatures.

SQLite keeps each workspace self-contained: the database is created inside the run directory and destroyed with it, so no state can leak between runs. Database-touching test cases run `async: false`. This costs nothing, because the only concurrency-sensitive task (`06-reservation-leak`) tests GenServer behaviour and never touches the database.

### Isolation

The agent must see the fixture and its visible tests, and nothing else — not held-out tests, not reference solutions, not other tasks, not the harness, not results. It therefore never opens `evalcode/`. It opens `runs/<run-id>/workspace/`, which the harness builds fresh per run.

Because `runs/` sits inside `evalcode/`, direnv walks up and loads the root `.envrc` automatically: the workspace shell has the correct Elixir with no per-run setup. `MIX_HOME` and `HEX_HOME` resolve to the evalcode root, so the hex cache is shared across runs.

### Overlays, not patches

A task's start state is produced by copying `overlay/` over a pristine fixture copy and removing any paths in `delete`. Patches were rejected: they rot whenever the fixture changes and are hard to read. An overlay file is just the stripped-down version of a real source file, so the start state can be read directly. Drift is caught automatically by `verify`.

`overlay/` mirrors the fixture's directory structure; each file replaces the fixture file at the same relative path. `delete` is a plain-text file, one fixture-relative path per line, blank lines and `#` comments ignored. `solution/` uses the same overlay semantics and is applied only by `verify`.

## CLI

```
evalcode list [--track domain|types|all]
evalcode start <task-id> --model <name> [--agent <name>] [--docs]
evalcode grade [<run-id>] [--duration <5m>]
evalcode report [--track domain|types|all]
evalcode verify [<task-id>]
```

### `start`

1. Create `runs/<run-id>/workspace/` from the pristine fixture.
2. Apply `overlay/`, then remove paths listed in `delete`.
3. Copy `visible/` into the workspace test directory.
4. Copy pre-warmed `deps/` and `_build/` in, so no network fetch is needed.
5. Create and migrate the SQLite database inside the run directory.
6. Write `TASK.md` into the workspace root.
7. If `--docs`, copy `docs/typing-primer.md` into the workspace.
8. Record `run.json` with task, model, agent, `docs_provided`, and `started_at`.
9. Print the workspace path.

### `grade`

1. Stamp `ended_at`, or use `--duration` if supplied.
2. Run the visible suite; record passed and total.
3. Copy `holdout/` in; run the full suite; record passed and total.
4. Run `mix compile --warnings-as-errors`; record `compile_clean` and `type_warnings_remaining`.
5. Checksum visible test files against the originals; set `tests_modified` if any were edited or deleted.
6. Scan sources for `@compile` / `@dialyzer` suppression attributes absent from the start state; set `suppressions_added`.
7. Append one record to `results/results.jsonl`.
8. Print the result.

### `verify`

For each task: build the start state and assert the expected tests **fail**; then apply `solution/` and assert everything **passes** and compiles clean. This is fail-to-pass validation. It requires no model, runs in CI, and is what catches overlay drift when the fixture changes.

`verify` also appends the compiler warnings it observes to `docs/observed-warnings.md`, so the primer's warning formats come from real compiler output rather than from memory.

## Fixture: `Warung`

A Phoenix 1.8 JSON API — no HTML, assets, or mailer.

- `Warung.Catalog` — `Product` (sku, name, price as `Decimal`, stock)
- `Warung.Orders` — `Order`, `OrderItem`, total calculation
- `Warung.Inventory` — stock reservations backed by a `ReservationServer` GenServer with TTL expiry
- `WarungWeb` — JSON controllers, API-key auth, error handling

The fixture compiles clean under `mix compile --warnings-as-errors` and its full suite passes.

## Track A — Domain (7 tasks)

| id | category | difficulty | task |
|---|---|---|---|
| `01-product-by-sku` | api | easy | Add `Catalog.get_product_by_sku/1`, a route, a controller action, and the 404 path. Smoke test: failure here means the setup is broken. |
| `02-money-rounding` | bugfix | easy-mid | Order totals are off by cents — float arithmetic crept into a `Decimal` pipeline. The visible test shows the symptom, not the cause. |
| `03-orders-n-plus-one` | ecto | mid | `Orders.list_orders/0` N+1s on items and products. Holdout counts queries via Ecto telemetry, so passing behaviour tests is not sufficient. |
| `04-discount-rules` | feature | mid | Percentage and fixed discounts, precedence rules, a cap. Requires a schema change, a migration, and context work. |
| `05-auth-plug-refactor` | refactor | mid-hard | Three controllers duplicate API-key auth; extract to a plug with behaviour unchanged. Pure pass-to-pass — the only way to score is to break nothing. |
| `06-reservation-leak` | otp | hard | `ReservationServer` leaks held stock when the reserving process dies. Requires `Process.monitor` and cleanup. Holdout kills holders concurrently. |
| `07-partial-shipments` | spec | hard | Implement a shipment state machine from a written spec in `task.md`. Multi-file; holdout covers transitions the visible tests never mention. |

## Track B — Types (5 tasks)

Each task isolates one Elixir 1.20 inference capability. All are single-module and small.

| id | 1.20 feature | the trap |
|---|---|---|
| `t01-guard-narrowing` | guard inference, `tuple_size` bounds | Guards declare `is_binary(x) or is_integer(x)` while the body handles one member. A `tuple_size(x) < 3` guard sits above an element access the compiler can prove is out of bounds. |
| `t02-map-key-sets` | `is_map_key` / `not_set()`, key tracking | A branch guarded by `not is_map_key(opts, :timeout)` reads `opts.timeout` — a verified bug. Elsewhere an upstream `Map.delete` makes a downstream access provably unreachable. |
| `t03-cross-clause-nil` | cross-clause narrowing | Two `nil` checks: one is dead code the compiler proves unreachable, the other is a real `nil` leaking into `String.upcase/1`. The model must tell them apart — deleting both, or guarding both, fails. |
| `t04-dynamic-boundary` | `dynamic()` compatibility | Decoded JSON flows into `Map.fetch!/2` with disjoint types. Requires a validation boundary at the edge, not `is_map/1` guards at the call site. |
| `t05-struct-contract` | inference across modules | A context returns `{:ok, t()} \| {:error, atom()} \| nil`; three callers each assume something different. One contract change, three call sites; holdout proves every branch stays reachable. |

`t03` is expected to discriminate most: the naive move treats both `nil` checks identically, and either choice is wrong for one of them.

### Anti-cheat

Track B's gate is `mix compile --warnings-as-errors`, which invites shortcuts. Each is countered:

| Escape hatch | Detection |
|---|---|
| Delete the `nil`/error branch to collapse the union | Holdout tests exercise the error path |
| Suppress with `@compile` / `@dialyzer` attributes | Source scan flags added suppression attributes |
| Launder types through `Map.get/2` into `any()` | Holdout asserts the specific error tuples still surface |

## Test visibility

Every task splits its tests:

- **Visible** — copied in at `start`. Covers the happy path and whatever `task.md` explicitly names. The agent can run and iterate against these, which mirrors real usage.
- **Holdout** — copied in only at `grade`. Covers edge cases, error paths, and anti-hardcoding assertions. **Holdout always re-runs the entire pre-existing suite**, so solving the task while breaking something else scores as a failure.

## Scoring

Three outcomes per task:

- `completed` — visible and holdout both fully pass, no tampering
- `partial` — visible pass, holdout fail. The model produced something that looks solved and is not.
- `failed` — visible tests do not pass

For Track B, `compile_clean` is an additional pass/fail criterion. For Track A it is recorded but informational, so it shows which models leave type warnings behind without distorting the completion score.

### Results schema

One line per graded task in `results/results.jsonl`:

```json
{"run_id":"2026-08-02-opus5-t03","task_id":"03-orders-n-plus-one",
 "model":"claude-opus-5","agent":"claude-code","track":"domain",
 "category":"ecto","difficulty":"mid",
 "started_at":"2026-08-02T09:14:02Z","ended_at":"2026-08-02T09:20:54Z","duration_s":412,
 "visible":{"passed":12,"total":12},"holdout":{"passed":5,"total":6},
 "compile_clean":true,"type_warnings_remaining":0,
 "tests_modified":false,"suppressions_added":false,"docs_provided":false,
 "status":"partial","tokens":null,"notes":""}
```

Either `tests_modified` or `suppressions_added` forces `status` to `failed` regardless of test results, and the reason is recorded in `notes`. They are separate fields because they are different kinds of cheating: one edits the grading criteria, the other silences the compiler.

`tokens` is reserved and always `null` in v1. A later collector fills it without a schema migration or a rewrite of the report.

### Report

`evalcode report` prints a table for the run just finished and regenerates `LEADERBOARD.md`:

```
model            domain   types   median   compile
claude-opus-5      6/7     4/5     6m12s      8/12
<next model>       5/7     2/5     9m40s      5/12
```

Tracks are scored separately. A model can be strong at shipping features and blind to type violations; averaging those into one number hides the thing being measured. The leaderboard also carries a per-category breakdown, so "strong on CRUD, falls over on OTP" stays visible.

## Documentation and the `--docs` flag

Elixir 1.20 was released 2026-06-03. Models with earlier training cutoffs have never seen this type system, which confounds Track B: a low score could mean missing knowledge or failed reasoning.

Default is **no docs in the workspace**. The compiler warning is itself the in-loop documentation — the model runs `mix compile`, reads real 1.20 violation text, and acts on it. Acting on unfamiliar compiler feedback is the capability worth measuring, and a primer hands over the answer before the model ever compiles.

`--docs` copies `docs/typing-primer.md` into the workspace, and `docs_provided` is recorded. **The gap between the two conditions is the measurement**: a model scoring 1/5 without docs and 4/5 with them has a knowledge problem, fixable with a `CLAUDE.md`. One scoring 1/5 both ways has a reasoning problem that no context can fix.

Two documents, two audiences:

| doc | audience | contents |
|---|---|---|
| `docs/typing-reference.md` | author | Full notes for writing tasks and reference solutions. Never enters a workspace. |
| `docs/typing-primer.md` | model, behind `--docs` | Curated one-pager: `dynamic()` semantics, guard inference, `not_set()`, cross-clause narrowing, warning formats. |

**The primer describes the type system and never the fixes.** Feature-level only. If it contains "when you see warning X, do Y" and that pairs with a task, it is an answer key and the track is worthless.

Sources: the official reference at `elixir.hexdocs.pm/gradual-set-theoretic-types.html` covers `dynamic()`, narrowing, and syntax, but has no guard inference mechanics and no warning formats. The 1.20 release post fills the guard gap. Warning formats come from `docs/observed-warnings.md`, generated by `verify` from real compiler output.

## Testing the harness

- `evalcode verify` is the primary integration test: every task's start state must fail as expected, and its reference solution must pass and compile clean. Runs in CI with no model involved.
- Unit tests cover `results.ex` (JSONL round-trip), `report.ex` (aggregation and formatting), `grader.ex` (ExUnit output parsing, tamper detection), and `workspace.ex` (overlay application and deletion).

## Known limitations

**Wall-clock timing is approximate.** `duration_s` runs from `start` to `grade`, so it includes the operator reading the task and stepping away. Three mitigations: `grade --duration 7m` overrides with the agent's own reported time; `report` shows median rather than mean; and a future transcript collector would give true agent time. Treat v1 speed as indicative — completion rate is the metric to trust.

**Sample size is small.** Twelve tasks with one run each is not statistically strong. Differences of one task between models are noise. Repeated runs of the same model give a variance estimate, which the JSONL already supports since each run is its own record.

**The fixture is synthetic.** It is written specifically for this benchmark, so it is cleaner and more consistent than real code. It measures capability on well-structured Elixir, which is a floor rather than a prediction of behaviour in a messy repository.

**Benchmark contamination is possible over time.** If the fixture is ever published, future models may train on it. Keeping the repository private preserves the benchmark's value.

## Implementation sequence

The harness is the small part; twelve tasks with overlays, two test suites each, and reference solutions are the bulk of the work.

1. Nix flake, `.envrc`, repository skeleton
2. Fixture app `Warung`, complete and passing
3. Harness: `workspace.ex`, `task.ex`, `grader.ex`, `results.ex`, `cli.ex`
4. Task `01-product-by-sku` and task `t01-guard-narrowing`, end to end
5. `verify`, proving both tasks fail-to-pass correctly
6. `report.ex` and `LEADERBOARD.md`
7. Remaining ten tasks against a known-good harness
8. `docs/typing-primer.md`, generated in part from `observed-warnings.md`

This is ordering, not a scope reduction. All twelve tasks are built.
